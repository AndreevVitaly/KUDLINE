# КУДЛАЙН

Корпоративная платформа ООО «КУДЛАЙН»: публичный сайт и рабочее место сотрудников на Django REST API, PostgreSQL, React + TypeScript и Django Admin. Направление развития — сопровождение заказа от заявки и совместного проектирования с клиентом до документов, производства и монтажа.

## Локальный запуск

1. Скопируйте `.env.example` в `.env` и укажите параметры PostgreSQL.
2. Backend:
   ```powershell
   cd backend
   python -m venv .venv
   .venv\Scripts\pip install -r requirements.txt
   .venv\Scripts\python manage.py migrate
   .venv\Scripts\python manage.py createsuperuser
   .venv\Scripts\python manage.py runserver
   ```
3. Frontend (в другом терминале):
   ```powershell
   cd frontend
   npm install
   npm run dev
   ```

Для разработки без PostgreSQL можно временно установить `USE_SQLITE=True` в `.env`.

## SPA history fallback

Vite development server автоматически возвращает `index.html` для прямых URL вроде `/about` и `/projects`.
Для production web-сервер должен делать то же самое. Например, для Nginx:

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

Файл `frontend/public/_redirects` содержит эквивалентное правило для совместимых static hosting-платформ.

## Клиентская база и заказы

Реализован фундамент клиентской базы и заказов: клиенты, контакты, банковские реквизиты, объекты, заказы и история статусов. Данные доступны через Django Admin и защищённый внутренний API рабочего места; в публичном API они не публикуются. Границы сущностей, политика удаления, будущая модель доступа личного кабинета и принцип snapshot для документов описаны в [docs/CLIENT_DATA_MODEL.md](docs/CLIENT_DATA_MODEL.md). Описание доступа в этом документе отражает первоначальный этап с Django Admin; текущий внутренний API описан ниже.

## Рабочее место менеджера

Защищённый интерфейс находится по адресу `http://127.0.0.1:5173/workspace/`. Он использует Django session authentication и CSRF, а внутренний API расположен под `/api/internal/`.

Первую административную учётную запись создайте интерактивно, не сохраняя пароль в Git:

```powershell
cd backend
$env:USE_SQLITE='True'
python manage.py createsuperuser
```

Для обычных сотрудников включите `is_staff` и назначьте группу `Менеджер` или `Руководитель` через Django Admin. Группы и модельные разрешения синхронизируются после `migrate`. Администратор-суперпользователь имеет полный доступ; руководитель получает обзор и рабочие операции в рамках выданных разрешений; менеджер работает с заявками, клиентами, объектами и заказами. Проверки выполняются backend-разрешениями, а не только интерфейсом.

Основные защищённые endpoints: `dashboard/`, `inquiries/`, `clients/`, `objects/`, `orders/`, `audit/`, `users/`. Реестры поддерживают пагинацию, поиск и фильтрацию. Изменения статусов заказов, ответственных и значимых данных фиксируются в журнале. Вложения заявок выдаются только через авторизованный endpoint; прямые URL `/media/inquiries/` заблокированы.

Будущие модули производства, сотрудников, финансов и документов обозначены в меню как планируемые и должны развиваться отдельными Django-приложениями со связью на `Order` по UUID.

## Roadmap: от заявки до готового изделия

План обновлён 1 ноября 2026 года. Этапы ниже — план разработки, а не перечень уже доступных функций. Сроки определяем после проверки объёма каждого этапа на реальных заказах.

Целевой сценарий: менеджер принимает заявку, связывает её с клиентом и объектом, фиксирует замеры, собирает изделие в конструкторе, обсуждает версии с клиентом, формирует документы и передаёт утверждённый комплект в производство. Клиент видит только предоставленные ему материалы; сотрудники работают в единой карточке заказа.

### Текущая основа

- [x] Публичный сайт и форма заявки.
- [x] Модели клиентов, контактных лиц, реквизитов, объектов и заказов с уникальными номерами.
- [x] Django Admin и рабочее место `/workspace/`: реестры, карточки, поиск, фильтры, ответственные и статусы.
- [x] Сессионная авторизация, модельные разрешения, журнал изменений и защищённое скачивание вложений заявок.
- [ ] Конструктор, версии макетов, клиентский кабинет, генерация документов и производственные задания.

Наличие базовых экранов не означает готовности всего процесса: перед расширением проверяем сквозной сценарий и права на реальных рабочих операциях.

### Этап 1. Полноценная карточка заказа и работа команды

**Результат:** сотрудник ведёт заказ на сайте без постоянного перехода в Django Admin.

- Завершить формы создания и редактирования клиентов, контактов, реквизитов, объектов и заказов в рабочем месте.
- Упростить путь «заявка → существующий или новый клиент → заказ» с явной проверкой дублей.
- Добавить позиции заказа: в одном заказе могут быть разные изделия, количество и варианты исполнения.
- Организовать замеры, фотографии объекта, исходные чертежи, задачи, сроки и внутренние комментарии внутри заказа.
- Согласовать матрицу ролей: администратор, руководитель, менеджер, проектировщик, производство, монтаж. Уточнить, кто видит все заказы, кто только назначенные и кому доступны цены.
- Проверять доступ на сервере к каждой карточке и файлу; новые роли вводить вместе с соответствующими экранами.

**Критерий завершения:** сотрудник принимает заявку, создаёт заказ с несколькими позициями, назначает ответственного, прикладывает замеры; другой сотрудник видит только разрешённые данные, а изменения сохраняются в истории.

### Этап 2. Каталог изделий и техническое задание

**Результат:** заказ описывается понятными параметрами, пригодными для конструктора и документов.

- Выделить семейства по примерам изделий: скамейки, урны, лестницы и ограждения, навесы и другие конструкции. Фотографии использовать как визуальные референсы; размеры, материалы и узлы уточнять отдельно.
- Для каждого семейства описать шаблоны, допустимые размеры в миллиметрах, материалы, профили, отделку, цвет, крепления и дополнительные опции.
- Первым пилотом предложить прямую скамейку на металлическом каркасе: длина, глубина, высота, спинка, подлокотники, дерево и покрытие. Выбор пилота подтвердить по частоте заказов и повторяемости производства.
- Создать справочники материалов и работ, версии расценок; различать предварительную оценку и утверждённую стоимость заказа.
- Зафиксировать форму ТЗ: назначение, количество, место установки, замеры, ограничения, референсы и вопросы к заказчику.

**Критерий завершения:** один реальный образец описан шаблоном и проверен мастером; все параметры имеют единицы, допустимые значения и правила совместимости.

### Этап 3. Конструктор MVP: параметры и размерный эскиз

**Результат:** менеджер вместе с клиентом собирает вариант изделия непосредственно на сайте.

- Реализовать выбор шаблона, изменение параметров и обновляемый 2D-эскиз с основными видами и размерами.
- Добавить выбор материалов и отделки, количество, предварительную спецификацию и оценку стоимости по согласованным правилам.
- Сохранять конфигурацию в позиции заказа, создавать копии вариантов, отменять изменения и восстанавливать сохранённую версию.
- Проверять параметры на сервере. Сохранять версию шаблона и правил расчёта, чтобы обновление каталога не меняло старый заказ.
- Выгружать эскиз и спецификацию в PDF; для нестандартного изделия оставлять путь через ТЗ и приложенный чертёж проектировщика.

Первый выпуск ограничиваем одним семейством и параметрическим 2D-редактором. Объёмную визуализацию добавляем после проверки геометрии и процесса согласования. Клиентский эскиз получает явный статус; выпуск рабочего чертежа требует отдельной проверки проектировщиком.

**Критерий завершения:** изменение длины пилотной скамейки согласованно обновляет эскиз, размеры и спецификацию; сохранённый вариант воспроизводится после повторного открытия, недопустимые параметры отклоняются.

### Этап 4. Совместное согласование и кабинет клиента

**Результат:** клиент обсуждает и подтверждает конкретную версию, а менеджер сохраняет историю решений.

- Добавить приглашения и отдельную модель доступа пользователей к клиентам и заказам; один клиент может иметь несколько представителей.
- Показывать клиенту разрешённые заказы, опубликованные макеты, документы и статусы; внутренние заметки и себестоимость оставлять сотрудникам.
- Добавить комментарии к версии, запрос изменений и статусы «черновик», «на согласовании», «согласовано», «заменено новой версией».
- При согласовании фиксировать версию, пользователя, дату и комментарий. Следующие изменения создавать новой версией с повторным согласованием.
- Защитить параллельное редактирование от незаметного перезаписывания чужих изменений. Совместное редактирование в реальном времени отложить до подтверждения необходимости.

Подтверждение макета в кабинете фиксирует рабочее согласование. Процесс подписания договора определяется отдельно.

**Критерий завершения:** два клиента не видят данные друг друга; клиент подтверждает версию №2, версия №3 требует нового согласования, а история №2 остаётся доступной.

### Этап 5. Документы из заказа

**Результат:** сотрудник формирует комплект документов из уже введённых данных.

- Начать с коммерческого предложения и спецификации; затем добавить согласованные компанией шаблоны договора, счёта, акта и задания в производство.
- Поддержать предпросмотр, PDF для выдачи и DOCX для редактируемых шаблонов, где это нужно сотрудникам.
- Хранить номер, тип, статус, автора, дату, версию шаблона и связь с заказом и согласованной конфигурацией.
- При выпуске сохранять неизменяемый снимок реквизитов сторон, позиций, цен, условий и версии макета. Изменение карточки клиента или каталога не меняет выпущенный файл.
- Разделить черновик, выпущенный документ и загруженный подписанный экземпляр; исправления выпускать новой версией с историей.
- Выдавать документы через защищённый API; доступ клиента предоставлять явно. Перед использованием утвердить состав и содержание шаблонов ответственным сотрудником компании.

**Критерий завершения:** из согласованного заказа получается КП и спецификация с совпадающими суммами и версиями; после смены реквизитов клиента ранее выпущенные документы остаются прежними.

### Этап 6. Производство, доставка и монтаж

**Результат:** цех и монтажники получают утверждённый комплект и отмечают выполнение работ.

- Формировать производственное задание из утверждённой версии: чертежи, состав, количество, материалы, отделка и сроки.
- Отслеживать операции, исполнителей, плановые и фактические даты, контроль качества, фотографии и замечания.
- Вести готовность, отгрузку, доставку и монтаж с учётом частичного выполнения позиций заказа.
- После запуска в производство изменения проводить отдельным согласованным изменением с оценкой влияния на стоимость и срок.
- Добавить учёт оплат и задолженности как отдельный модуль; бухгалтерские интеграции и склад планировать после проверки рабочего процесса.

**Критерий завершения:** пилотный заказ проходит от согласованного комплекта до монтажа и закрывающих документов; видно, какую версию изготовили и кто подтвердил качество.

### Этап 7. Расширение конструктора

**Результат:** проверенная схема распространяется на следующие семейства изделий.

- Добавлять урны, ограждения, лестницы и навесы по отдельности, со своими параметрами и проверкой специалистом.
- Ввести 3D-просмотр, варианты размещения на объекте и сравнение исполнения, если они помогают клиенту принимать решение.
- После проверки производственных требований рассмотреть экспорт DXF и интеграцию с используемой CAD-системой.
- Автоматизировать деталировку, ведомости материалов и раскрой только для проверенных шаблонов; сложные конструкции направлять проектировщику.

**Критерий завершения каждого расширения:** контрольный образец проходит полный путь от параметров до проверенной документации и изготовления; визуализация соответствует сохранённой конфигурации.

### Общие правила реализации

- Сохранить React и Django как основу; новые предметные модули подключать к существующему заказу, без дублирования базы клиентов.
- Предлагаемая цепочка данных: `Order → OrderItem → DesignRevision → Approval → Document / ProductionTask`. Это будущие сущности, их ещё нет в проекте.
- Хранить исходные параметры, версию схемы, шаблона и расчёта вместе с версией изделия; картинка или PDF являются производными файлами.
- Предусмотреть приватное хранение всех материалов заказа, ограничения загрузок, журнал выдачи доступа и отзыв приглашений.
- Перед использованием командой на сервере настроить PostgreSQL, HTTPS, хранение секретов, резервное копирование базы и файлов с проверкой восстановления, журнал ошибок и тестовую среду для обновлений.
- Проверять разграничение доступа, версии, расчёты и переходы статусов автоматическими тестами, а каждый этап принимать сквозным сценарием с сотрудником.

### Ближайший практический шаг

Взять один завершённый заказ на скамейку и собрать эталонный комплект: замеры, исходный чертёж, материалы и профили, состав деталей, правила стоимости, образец КП и спецификации. На его основе завершить карточку заказа и описать первый шаблон конструктора. После этого реализовать путь «заказ → параметры → эскиз → версия → КП» для сотрудника, затем подключать согласование клиентом.

До начала конструктора нужно уточнить: самое частое изделие, обязательные размеры и ограничения, кто проверяет чертежи, как считается цена, какие документы реально используются и кто имеет право их выпускать. Присланные фотографии помогают определить семейства и варианты внешнего вида; технические характеристики по ним не считаются подтверждёнными.
